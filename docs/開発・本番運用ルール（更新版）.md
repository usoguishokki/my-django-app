# 開発・本番運用ルール（完成版）

最終更新日: 2026年7月18日
対象システム: 点検カード（Django / Oracle / IIS FastCGI）
文書ステータス: 運用基準

---

## 1. 目的

開発環境と本番環境を分離し、次の作業を安全かつ再現可能に行う。

- 機能追加・不具合修正
- 秘密情報の保護
- Gitによる変更管理
- Python依存関係の更新
- Oracleマイグレーション
- 静的ファイルの反映
- IISアプリケーションの再起動
- 障害時のロールバック
- 本番反映記録の保存

本書に記載のない例外対応を行う場合は、実行前に影響範囲と復旧方法を確認する。

## 3. サポート期限とアップグレード方針

現在の基準環境は次のとおり。

```text
Python 3.9.6
Django 4.2.14
```

Python 3.9系とDjango 4.2系は、すでに公式サポートが終了している。現在の構成を恒久運用しない。

### 必須方針

- 新規機能開発と並行して、Python・Django更新計画を作成する
- 移行先はサポート中のPythonとDjango LTSを基本とする
- `cx_Oracle`、`pyodbc`、`libsass`、`django-sass-processor`、`wfastcgi`、IIS FastCGIとの互換性を検証する
- 本番を直接アップグレードしない
- 新しい仮想環境を別名で作成し、検証後に切り替える
- アップグレードは通常の機能デプロイと分けて実施する

## 4. Django settings運用

### 4.1 基本方針

- `myproject/settings.py` の一本運用とする
- `myproject.settings` を参照する
- `settings.py` はGit管理する
- `settings.py` と `settings/` ディレクトリを共存させない
- 開発・本番で同一の `settings.py` を使用する
- 秘密情報と環境差分は `.env` に置く
- `settings.py` に接続先・ユーザー名・パスワードを直書きしない

`.env` はプロジェクト位置に依存しないよう、次の形式で読み込む。

```python
load_dotenv(BASE_DIR / ".env")
```

### 4.2 環境変数化する項目

```text
DJANGO_SECRET_KEY
DJANGO_DEBUG
DJANGO_ALLOWED_HOSTS

ORACLE_DATABASE_NAME
ORACLE_DATABASE_USER
ORACLE_DATABASE_PASSWORD

MARP_DB_DRIVER
MARP_DB_SERVER
MARP_DB_PORT
MARP_DB_NAME
MARP_DB_USERNAME
MARP_DB_PASSWORD
```

### 4.3 SECRET_KEY

- 開発と本番で異なる値を使用する
- 本番のSECRET_KEYを開発PCへコピーしない
- 本番のSECRET_KEYを計画なしに変更しない
- 変更すると既存セッションや署名済みデータへ影響する可能性がある

## 5. `.env`・秘密情報運用

### 5.1 基本ルール

- `.env` はGit管理しない
- `.env.example` のみGit管理する
- `.env.example` に実値を書かない
- `.env` の内容をターミナル、ログ、チャット、メールへ貼り付けない
- 設定確認では値ではなく `SET` / `MISSING` のみ表示する
- 本番 `.env` はIIS実行ユーザーと管理者だけが読み取れるようにする
- `.env` バックアップも秘密情報として扱う
- 不要な旧バックアップは保存期限を決めて削除する

確認:

```powershell
git check-ignore -v .env
git status --short .env
```

正常時、`.env` は `.gitignore` で除外され、`git status` には表示されない。

### 5.2 設定有無の確認

```powershell
python -c "
import os
from dotenv import load_dotenv

load_dotenv()

keys = [
    'DJANGO_SECRET_KEY',
    'DJANGO_DEBUG',
    'DJANGO_ALLOWED_HOSTS',
    'ORACLE_DATABASE_NAME',
    'ORACLE_DATABASE_USER',
    'ORACLE_DATABASE_PASSWORD',
    'MARP_DB_DRIVER',
    'MARP_DB_SERVER',
    'MARP_DB_PORT',
    'MARP_DB_NAME',
    'MARP_DB_USERNAME',
    'MARP_DB_PASSWORD',
]

for key in keys:
    print(f'{key}=' + ('SET' if os.getenv(key) else 'MISSING'))
"
```

### 5.3 禁止

- `.env` を `git add -f` する
- `.env` をZIPへ含めて共有する
- 本番 `.env` を開発環境へコピーする
- `.env` バックアップを共有フォルダーへ無制限に保存する
- 秘密値をソースコードへ一時的に直書きする

## 6. Gitブランチ運用

### 6.1 ブランチの役割

| ブランチ | 用途 |
|---|---|
| `main` | 本番反映可能な確定版 |
| `feature/*` | 機能開発・修正・検証 |
| `backup/*` | 大規模作業前や未整理状態の退避 |

### 6.2 開発開始

```powershell
cd E:\repos\myproject
.\venv\Scripts\Activate.ps1

git switch main
git fetch origin
git pull --ff-only origin main
git switch -c feature/<機能名>
```

例:

```powershell
git switch -c feature/parts-search
```

### 6.3 mainへ統合

```powershell
git status --short
```

作業ツリーがクリーンであることを確認後:

```powershell
git switch main
git fetch origin
git pull --ff-only origin main
git merge --ff-only feature/<機能名>
git push origin main
```

同期確認:

```powershell
git rev-list --left-right --count origin/main...main
```

正常時:

```text
0       0
```

### 6.4 禁止

- `main` 上で長期間の機能開発を続ける
- 未コミット変更がある状態でブランチを整理する
- 本番でマージコミットを作る
- 本番で `git pull` の代わりに無確認で `git merge` する
- 内容未確認で `git clean -fd` を実行する

## 7. バックアップブランチ

### 7.1 作成

```powershell
git switch -c backup/full-dev-state-YYYYMMDD

git status --short
git add -A
git diff --cached --name-status

git commit -m "Backup full development state before deployment"
git push -u origin backup/full-dev-state-YYYYMMDD
```

### 7.2 注意

- `.env`、バックアップ、実データ、`node_modules` が含まれていないことを確認する
- 日付と目的が分かる名前を使用する
- `backup/current-dev-state` のような同一名を使い回さない
- 本番安定確認までは削除しない

### 7.3 作業ツリーだけ復元

```powershell
git switch feature/<機能名>

git restore `
    --source=backup/full-dev-state-YYYYMMDD `
    --worktree `
    -- .
```

この操作では復元内容は未コミット状態になる。

## 9. Python依存関係

### 9.1 基本ルール

- `pip` ではなく `python -m pip` を使う
- 追加したパッケージは `requirements.txt` に固定バージョンで記録する
- 開発と本番で同一バージョンを使う
- 本番反映後に `python -m pip check` を実行する
- インストール失敗時はデプロイを続行しない

### 9.2 requirements.txtの文字コード

`requirements.txt` はUTF-8で管理する。

現在のUTF-16 LEからUTF-8への変換は、通常の機能変更と分けた専用コミットで行う。

変換後の確認:

```powershell
python -m pip install --dry-run -r requirements.txt
git diff -- requirements.txt
```

UTF-16、Shift_JIS、意図しないBOM付き形式で新規作成しない。

### 9.3 本番での依存更新判定

```powershell
$requirementsChanged = git diff `
    --name-only `
    $beforeCommit `
    $afterCommit `
    -- requirements.txt

if ($requirementsChanged) {
    python -m pip install -r requirements.txt

    if ($LASTEXITCODE -ne 0) {
        throw "requirements.txtの適用に失敗しました。"
    }
}

python -m pip check

if ($LASTEXITCODE -ne 0) {
    throw "Python依存関係の整合性確認に失敗しました。"
}
```

## 10. Oracle DB・マイグレーション

### 10.1 共有DBの重要事項

開発環境と本番環境は同じOracle DBを使用する。

そのため、開発環境での登録・更新・削除・マイグレーションは本番データへ直接影響する。

### 10.2 開発環境で許可する確認

```powershell
python manage.py makemigrations --check --dry-run
python manage.py migrate --plan
python manage.py showmigrations myapp
```

### 10.3 開発環境での migrate

通常の開発作業として次を実行しない。

```powershell

```

マイグレーション適用は、担当者・対象・バックアップ・復旧方法を確認した本番反映作業として一度だけ行う。

### 10.4 適用前の確認事項

- 対象マイグレーション名
- 対象テーブル・列
- 追加・変更・削除内容
- データ変換の有無
- reversibleか
- ロールバック方法
- Oracle RMANバックアップの状態
- アプリ停止が必要か
- 既存コードとの互換性

### 10.5 適用

```powershell
python manage.py migrate --plan
```

## 15. 本番のローカル差分

`git status --short` に差分がある場合、反映を開始しない。

次の順で対応する。

1. `git diff` で内容を確認
2. 必要ならリポジトリ外へバックアップ
3. 本番で直接修正されたものか確認
4. 生成物かソースか確認
5. 対象ファイルを限定して復元
6. 再度 `git status --short` を確認

例:

```powershell
git diff -- myapp/static/css/pages/example.css

Copy-Item `
    .\myapp\static\css\pages\example.css `
    "$backupDir\example.css"

git restore -- myapp/static/css/pages/example.css
```

無条件のフォルダー単位restoreは禁止する。

```powershell
git restore myapp/static/css
```

## 17. デプロイ中にエラーが発生した場合

### 17.1 migrate前の失敗

マイグレーションを実行していない場合は、緊急復旧として反映前コミットへ戻せる。

```powershell
git reset --hard $beforeCommit
python manage.py collectstatic --noinput
Start-WebAppPool -Name $appPoolName
```

これは本番ローカルの緊急復旧であり、恒久対応ではない。本番安定後、開発環境の `main` にrevertコミットを作成して同期し直す。

### 17.2 migrate後の失敗

コードだけを戻さない。

次を確認する。

- 適用済みマイグレーション
- reversibleか
- データ変更の有無
- 旧コードとの互換性
- DBバックアップからの復元が必要か
- アプリを起動してよいか

判断が完了するまで、原則としてアプリケーションプールを停止したままにする。

```powershell
$urls = @(

    try {
        $response = Invoke-WebRequest `

            Write-Host "STATUS=ERROR URL=$url"
            Write-Host $_.Exception.Message
        }
    }
}
```

## 19. ロールバック

### 19.1 基本方針

通常のロールバックは、開発環境で `git revert` により打ち消しコミットを作る。

```powershell
cd E:\repos\myproject
.\venv\Scripts\Activate.ps1

git switch main
git pull --ff-only origin main
git revert <問題を起こしたコミットID>
git push origin main
```

本番では標準手順で反映する。

```powershell
git fetch origin
git merge --ff-only origin/main
python manage.py collectstatic --noinput
Restart-WebAppPool -Name "<点検カードのアプリプール名>"
```

### 19.2 reset --hard

`git reset --hard` は本番停止中の緊急一時復旧だけに限定する。

注意:

- 本番ローカルの `main` が `origin/main` より後退する
- 次回pullで問題コミットが再反映される
- 必ず後からrevertコミットを作成する
- 実行前にコミットIDと作業ツリーを確認する

### 19.3 DBを含むロールバック

コードとDBを別々に判断する。

```powershell
python manage.py migrate myapp <戻し先マイグレーション>
```

ただし、次を確認せず実行しない。

- reversibleか
- データ消失
- 他機能への影響
- 共通Oracle DBへの影響
- RMANバックアップ
- コードとの整合性

## 23. 禁止事項

- 本番でPython・JavaScript・SCSS・CSS・テンプレートを直接編集する
- 本番で `settings.py` を直接編集する
- `.env` や秘密情報をGitへ追加する
- `node_modules` をGitへ追加する
- 作業ツリーが汚れた状態で本番反映する
- 内容未確認で `git restore`、`git reset --hard`、`git clean -fd` を実行する
- 開発環境から日常的に共有Oracle DBへ `migrate` する
- DBバックアップなしで不可逆マイグレーションを実施する
- 通常デプロイで `npm run build` を実行する
- 通常デプロイで `iisreset` を実行する
- migrate後の障害でコードだけを無条件に戻す
- 本番エラー時に秘密値を画面へ出力する

## 26. 最終原則

- `main` は常に本番反映可能な状態にする
- 機能開発は `feature/*` で行う
- 大規模変更前は `backup/*` へ退避する
- `settings.py` はGit管理し、秘密情報は `.env` に置く
- 開発と本番の `.env` を分離する
- 本番は `DEBUG=False`
- 本番を直接編集しない
- pull相当の反映はFast-forwardだけを許可する
- 本番差分を無条件に削除しない
- SCSSを編集元とし、CSSは開発で生成する
- staticfilesは本番で収集する
- IIS全体ではなく対象アプリケーションプールを操作する
- 共有Oracle DBへの変更は本番変更として扱う
- ロールバックは `git revert` を基本とする
- migrate後の障害ではコードとDBを一体で判断する
- 本番反映後は必ずHTTP・ブラウザー確認を行う
- すべての本番反映を記録する
